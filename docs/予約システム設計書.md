# HERLOCK 独自予約システム 設計書（Phase 1）

- 作成日: 2026-07-05 ／ 更新日: 2026-07-06（v1.2 人数無制限・飲み放題オプション等の仕様変更反映）
- ステータス: ドラフト（承認待ち）
- 対象: 飲食店LP（herlock_lp）に組み込む独自予約システム

---

## 1. 目的と方針

- ホットペッパーの管理費を削減するため、LP経由の予約を独自システムで受け付ける
- ホットペッパーは当面**併用**（集客経路として維持）。ダブルブッキングは管理画面へのHP予約手動登録で防止
- 決済機能は**今回は実装しない**（店頭決済のまま。将来Stripe等を追加できる設計だけ残す）
- 月額コストほぼ0円（無料枠内）で運用する

## 2. 全体構成

```
[お客様]
   │ 予約フォーム (reserve.html … LPに追加する静的ページ)
   ▼
[Cloudflare Turnstile] ボット防止
   ▼
[Supabase Edge Function] create_reservation（サーバー側処理）
   ├─ 残席チェック＋予約確定（トランザクション）
   ├─ Resend で確認メール送信（Reply-To: 店のGmail）
   ├─ LINE公式アカウントBot で店長に通知
   └─ Google カレンダーに予定を自動登録
   ▼
[Supabase Postgres] 予約データ（RLSで保護）

[スタッフ] ──ログイン──▶ [管理画面 admin.html] 予約一覧 / HP予約登録 / 空き枠設定
```

## 4. 残席管理ロジック（二重予約防止の設計）

**「枠のロック」ではなく「残席数の管理」で行う。**

1. 各予約は `start_time` から `stay_minutes`（コース設定 or 既定値120分）の間、席を占有するとみなす
2. ある枠の残席 = 席種の総席数 − その時間帯に重なる confirmed 予約の人数合計（**HP・電話予約も含む**）
3. 残席 ≥ 申込人数 なら予約可。足りない席種のみ「満席」表示
4. 予約確定はDBのトランザクション内で「残席再チェック→INSERT」を原子的に実行（PostgreSQLの行ロックを1秒未満だけ使用）。同時アクセスでの定員超過を確実に防ぐ

→ 少人数予約が入っても残席がある限り受付継続。お客様に「ロック」が見えることはない。

**団体（9名以上）の扱い（v1.2）**: 残席の自動判定では弾かず**人数無制限で仮受付（pending）**する。店からの電話確認後にスタッフが「確定」操作（席割・2F解放の判断込み）を行う。
仮受付の残席への反映は**席割当が決まった時点**（Phase 3の管理画面操作）で行う。それまでの間に同時間帯へ他の予約が入る可能性はあるが、団体は必ず電話確認を挟むため、その時点でスタッフが席繰り・2F解放で調整する運用とする（Phase 2実装と一致）。

## 5. お客様側の予約フロー

1. LPの「予約」ボタン → reserve.html
2. 日付選択 → 空き状況をカレンダー表示（○△×）
3. 時間・人数・コースを選択
   - コースなし（**席のみ予約**）も可。席のみの場合は**単品飲み放題プラン（+3,500円）**を選択可
   - スタンダード・プレミアム・宮崎牛コースは**飲み放題追加（+1,500円）**を選択可（女子会・宴会限定は込み）
4. 名前・電話・メール・要望を入力 → Turnstile通過 → 送信
5. 確定/仮受付の分岐（v1.2）
   - **1〜8名**: 残席があれば即時確定 → 確認メール（キャンセル用URL付き）
   - **9名以上**: **人数無制限で仮受付** → 「ご予約内容の確認のため、店舗よりお電話いたします」というメールを送信し、店から電話 → スタッフが管理画面で確定
   - 団体予約のフォームおよびメールには次の注意文言を表示する（v1.3）:
     「※ご来店の1週間前〜2日前の間に5名以上の人数変更がある場合、キャンセル料が発生する可能性があります。人数の変更は都度ご連絡ください。」
6. 前日にリマインドメール自動送信
7. キャンセルはメール内URLから可能（**前日18:00まで**。期限後は電話のみ。キャンセル発生時はスタッフにLINE通知）
8. **Web予約の受付期限は来店前日の営業時間内まで**（当日予約は電話のみ・v1.2）

## 6. 管理画面（admin.html — スマホ対応）

- **要電話確認（仮受付）一覧**: 9名以上のWeb予約が入ると最上部に表示。電話後に「確定」or「調整」or「キャンセル」をタップ（v1.2）
- **今日の予約**: 当日一覧。来店したら「着席」タップ、来なければ「無断キャンセル」記録
- **予約一覧**: 日付・状態で絞り込み。変更・キャンセル操作
- **HP予約の登録**: ホットペッパー・電話予約を手入力 → 残席に自動反映（ダブルブッキング防止の要）
- **営業日カレンダー**: 月表示のカレンダーで休業/営業をタップ切替（不定休・月曜団体営業・振替休に対応）
- **顧客リスト**: 来店回数・最終来店・メモの閲覧と編集。電話番号・名前で検索（v1.1）
- **空き枠設定**: 席数の一時変更（貸切等）
- **設定**: コース管理、営業時間、**予約受け取りメールアドレスの追加/削除、Reply-To変更**（v1.1）
- ログイン必須（Supabase Auth）。スタッフ全員が自分のアカウントを持つ（共有パスワードにしない）

## 7. 通知設計

| タイミング | お客様（メール/Resend） | スタッフ |
|---|---|---|
| 仮受付（9名以上・v1.2） | 「店舗よりお電話いたします」メール | **LINE通知（要電話マーク付き）**＋登録済みメールへ転送 |
| 予約確定 | 確認メール（Reply-To: 設定画面で変更可） | LINE即時通知＋Googleカレンダー登録＋**登録済みメールアドレス（複数可）へ転送** |
| 前日 | リマインドメール | ─ |
| キャンセル | キャンセル確認メール | **LINE即時通知**＋カレンダーから削除 |

- 送信元は独自ドメイン（SPF/DKIM設定で迷惑メール入りを防止）。お客様の返信は店のGmailに届く
- Googleカレンダーは店の共有カレンダーに登録し、スタッフ全員が閲覧可

### 7.1 LINE通知の方式（LINE公式アカウントに一本化）

将来の公式LINE運用と同一アカウントで一本化する。LINEのpush送信は「受信人数分」課金されるため（無料枠は月200通）、コストを抑える構成は次のとおり。

- **採用案**: 新規予約・キャンセルは Messaging API で**店長1人にpush**（1通知=1通）。スタッフ全員へは**Google共有カレンダー**で共有
- 月200通を超える規模になったら、ライトプラン（月5,000円）に上げてスタッフグループへの直接通知に切り替え可能（コード変更は最小）
- 参考: LINE Developers 料金仕様・LYPプラン表（2026-07時点で確認）

## 8. セキュリティ設計

1. **RLS（行レベルセキュリティ）**: 予約・顧客テーブルは既定で全拒否。匿名ユーザーは読み書き不可、予約作成はEdge Function（サーバー側）経由のみ。スタッフはログイン後のみ閲覧可
2. **秘密鍵の管理**: service_role キー・APIキーはSupabaseの環境変数のみに保存。HTML/JSには公開用キーしか置かない
3. **ボット・スパム対策**: Cloudflare Turnstile＋同一IP・同一電話番号の連続予約制限
4. **入力値検証**: サーバー側で全項目を検証（人数上限、日付範囲、文字数、形式）
5. **顧客リストの保護**（v1.1変更: 匿名化はせず顧客リストとして蓄積する）: 取得項目は名前・電話・メールのみに限定。閲覧はログイン済みスタッフのみ・操作は監査ログに記録・Supabaseの保存時暗号化＋日次バックアップ。予約フォームに利用目的（予約管理・来店案内）を明記したプライバシーポリシーを掲載し、お客様から削除依頼があれば個別に削除できる機能を管理画面に用意（個人情報保護法対応）
6. **キャンセルURL**: 推測不能な乱数トークン。第三者が他人の予約を操作できない
7. **監査**: スタッフの操作（誰がいつ変更したか）を記録
8. **通信**: 全ページHTTPS。管理画面はログイン必須＋セッション有効期限設定

## 9. 運用ルール（HP併用期間）

## 11. 店舗確定情報（2026-07-05 ヒアリング）

### 営業時間（確定）

| 曜日 | 営業時間 | L.O. |
|---|---|---|
| 火〜土 | 18:00〜25:30（翌1:30） | 25:00（翌1:00） |

- **不定休あり（v1.1）**: シェフの休み等で月7回程度の休業日が発生する。また月曜に団体予約が入った場合は月曜営業とし、代わりに火曜や日曜が休みになることがある。→ 管理画面の営業日カレンダーで日単位に上書き設定（3. special_days参照）
- 深夜営業のため、24時以降の時刻は「営業日基準」で扱う（例: 土曜25:00の予約は土曜の営業日に属する）。DB内部では日付をまたぐ時刻を正しく処理する
- 予約枠の刻みは**30分で確定**（v1.1）
