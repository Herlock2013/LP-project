# 予約システム セットアップ手順書（Phase 2）

作成したファイルを動かすための手順です。上から順に進めてください。
所要時間の目安: 1〜2時間（DNSの反映待ちを除く）

## 用意するもの

- Supabase アカウント（無料）… データベースとAPI
- Resend アカウント（無料）… メール送信
- Cloudflare アカウント（既存。Pagesで利用中のもの）… ボット防止とDNS設定

## 手順1: Supabase プロジェクトを作る

1. https://supabase.com にアクセスして「Start your project」からサインアップ（GitHubアカウントでOK）
2. 「New project」を押す
   - Name: `herlock-reservation`
   - Database Password: 長いパスワードを生成してパスワード管理アプリに保存
   - Region: `Northeast Asia (Tokyo)` を選ぶ
3. 作成完了まで数分待つ

## 手順2: データベースを作る

1. 左メニューの「SQL Editor」を開く
2. このリポジトリの `supabase/schema.sql` の中身を全部コピーして貼り付け、「Run」を押す
3. 「Success」と出ればOK。左メニュー「Table Editor」に `reservations` などのテーブルが並んでいるか確認

## 手順3: Resend（メール送信）を設定する

1. https://resend.com でサインアップ
2. 「Domains」→「Add Domain」で `diningbar-herlock.com` を追加
3. 表示されるDNSレコード（SPF/DKIM）を Cloudflare のDNS設定に追加する
   - Cloudflareダッシュボード → 対象ドメイン → DNS → 「レコードを追加」で、Resendに表示された値をそのまま入力
4. Resend側で「Verified」になるまで待つ（数分〜数時間）
5. 「API Keys」→「Create API Key」でキーを作成し、控えておく（あとで使う）

## 手順4: Turnstile（ボット防止）を設定する

1. Cloudflareダッシュボード → 「Turnstile」→「Add site」
2. Domain に `diningbar-herlock.com` を入力、Widget Mode は「Managed」
3. 表示される **Site Key**（公開してよい方）と **Secret Key**（秘密の方）を控える

## 手順5: Edge Functions（予約処理）を配置する

パソコンのターミナルで実行します。

```bash
# Supabase CLI をインストール（Mac）
brew install supabase/tap/supabase

# ログインと紐付け（PROJECT_REF はSupabaseの Settings > General で確認）
supabase login
cd LP-projectのフォルダ
supabase link --project-ref PROJECT_REF

# 秘密情報を登録（値は自分のものに置き換える）
supabase secrets set RESEND_API_KEY=re_xxxxxxxxx
supabase secrets set RESEND_FROM="HerLock 予約 <reserve@diningbar-herlock.com>"
supabase secrets set TURNSTILE_SECRET_KEY=0x_xxxxxxxxx
supabase secrets set SITE_URL=https://diningbar-herlock.com
supabase secrets set CRON_SECRET=適当な長いランダム文字列

# 4つの関数をデプロイ
supabase functions deploy create-reservation --no-verify-jwt
supabase functions deploy get-availability --no-verify-jwt
supabase functions deploy cancel-reservation --no-verify-jwt
supabase functions deploy send-reminders --no-verify-jwt
```

> **注意**: Secret Key や API Key は絶対に HTML や Git にコミットしないこと。登録先は `supabase secrets` のみ。

## 手順6: reserve.html の設定を書き換える

`reserve.html` を開いて2か所を書き換えます。

1. `FUNCTIONS_BASE` の `YOUR_PROJECT_REF` を自分のプロジェクトIDに変更
   例: `https://abcdefghij.supabase.co/functions/v1`
2. `TURNSTILE_SITE_KEY_HERE` を手順4で控えた **Site Key**（公開してよい方）に変更

書き換えたら Cloudflare Pages にデプロイ（いつものgit push）。

## 手順7: リマインドメールの定期実行を設定する

Supabase の SQL Editor で以下を実行（URLとCRON_SECRETは自分の値に置き換え）。
毎日 JST 10:00（UTC 1:00）に前日リマインドを送信します。

```sql
create extension if not exists pg_cron;
create extension if not exists pg_net;

select cron.schedule(
  'send-reminders-daily',
  '0 1 * * *',
  $$
  select net.http_post(
    url := 'https://PROJECT_REF.supabase.co/functions/v1/send-reminders',
    headers := '{"Authorization": "Bearer CRON_SECRETの値", "Content-Type": "application/json"}'::jsonb,
    body := '{}'::jsonb
  );
  $$
);
```

## 手順8: 動作テスト（公開前に必ず全部やる）

1. reserve.html を開き、2名で明日以降の予約 → 確認メールが届くか
2. 満席テスト: 同じ枠に予約を入れ続け、席が埋まったら「満席」表示になるか
3. 9名で予約 → 「仮受付」メールになるか、店側メールに【要電話確認】が付くか
4. 確認メールのキャンセルURL → キャンセルできるか、店側にキャンセル通知が来るか
5. 前日18:00以降のキャンセル → 「お電話ください」と拒否されるか（テストは settings の cancel_deadline_min を一時変更すると楽）
6. 休業日（月曜）がカレンダーで×になっているか
7. 当日の日付が選べないか（前日締切）
8. スマホ（iPhone/Android）で表示崩れがないか

## 設定値の変更方法（覚えておくと便利）

管理画面ができるまで（Phase 3まで）は、Supabase の Table Editor から直接変更します。

- **予約受け取りメールを追加**: `settings` テーブルの `notification_emails` を編集（例: `{"info@example.com","tencho@example.com"}`）
- **返信先アドレス**: `settings` の `reply_to_email`
- **臨時休業日を入れる**: `special_days` に行を追加（date=対象日, type=`closed`）
- **月曜営業にする**: `special_days` に行を追加（date=対象日, type=`open`, open_min=1080, last_entry_min=1410, close_min=1530）
- **席数の変更**: `seat_types` の `total_capacity` などを編集

時刻は「分」で入力します: 18:00→1080 / 23:30→1410 / 24:00→1440 / 25:00→1500 / 25:30→1530

## Phase 3: 管理画面のセットアップ

### 手順9: スタッフアカウントを作る

1. Supabaseダッシュボード → 「Authentication」→「Users」→「Add user」→「Create new user」
2. スタッフごとにメールアドレスとパスワードを設定して作成（共有アカウントにしない）
3. **重要**: 「Authentication」→「Sign In / Up」(または Providers > Email) で **新規サインアップを無効化**する（Allow new users to sign up をOFF）。これをしないと第三者が勝手にアカウントを作れてしまう

### 手順10: スタッフ用の権限を設定する

SQL Editorで `supabase/admin-policies.sql` の中身を貼り付けて「Run」。

### 手順11: 通知用関数のデプロイと管理画面の設定

```bash
cd LP-projectのフォルダ
# JWT検証あり（--no-verify-jwt を付けない）でデプロイ
supabase functions deploy admin-notify
```

`admin.html` の `SUPABASE_ANON_KEY_HERE` を自分の anon キー（公開可の方。Settings > API Keys の `anon` `public`）に書き換えて、git push。

### 手順12: 管理画面の動作テスト

1. `https://diningbar-herlock.com/admin.html` を開いてスタッフのメール/パスワードでログイン
2. **ログインせずに開いた場合にデータが見えないこと**を必ず確認（シークレットウィンドウで）
3. 「登録」タブからHP予約を手入力 → 「今日」「一覧」に出るか
4. 9名のWeb予約を入れて「仮受付」タブ → 席を選んで「電話済み・確定」→ お客様に確定メールが届くか
5. 「休業日」タブで来週の月曜をタップ → 営業日にできるか。予約フォームのカレンダーに反映されるか
6. 「顧客」タブで検索・メモ保存ができるか
7. 「設定」タブで通知先メールを追加 → テスト予約で追加先にも届くか

### 手順14: LINE公式アカウントの通知設定

1. https://developers.line.biz にアクセスし、LINEアカウントでログイン
2. プロバイダーを作成（名前: HerLock など）→ 「Messaging API」チャネルを作成（これが公式アカウントになる。将来のお客様向け配信にも使える）
3. チャネル基本設定の「チャネルシークレット」を控える
4. 「Messaging API設定」タブ →「チャネルアクセストークン（長期）」を発行して控える
5. ターミナルで登録:
```bash
supabase secrets set LINE_CHANNEL_ACCESS_TOKEN=発行したトークン
supabase secrets set LINE_CHANNEL_SECRET=チャネルシークレット
```
6. webhook関数をデプロイ:
```bash
supabase functions deploy line-webhook --no-verify-jwt
```
7. LINE Developersの「Messaging API設定」→ Webhook URL に
   `https://nxqnyhfdbiyuxahutkvf.supabase.co/functions/v1/line-webhook` を設定し「Webhookの利用」をON
   （「応答メッセージ」はOFF推奨）
8. **店長のLINE**で公式アカウントを友だち追加し、何かメッセージを1通送る
9. SQL Editorで店長のユーザーIDを確認:
```sql
select detail, created_at from audit_log
where action = 'line_user_capture' order by created_at desc limit 5;
```
10. 表示された `userId`（Uで始まる文字列）を登録:
```bash
supabase secrets set LINE_TO=Uxxxxxxxxxxxxxxxx
```

### 手順15: Googleカレンダー連携

1. https://console.cloud.google.com で新しいプロジェクトを作成（名前: herlock-reservation）
2. 「APIとサービス」→「ライブラリ」→「Google Calendar API」を検索して有効化
3. 「APIとサービス」→「認証情報」→「認証情報を作成」→「サービスアカウント」→ 名前を付けて作成（ロールは不要）
4. 作成したサービスアカウント →「キー」タブ →「鍵を追加」→「新しい鍵を作成」→ JSON → ダウンロード
5. 店のGoogleアカウントでカレンダーを1つ作成（例: 「HerLock予約」）。スタッフ全員に共有
6. そのカレンダーの「設定と共有」→「特定のユーザーまたはグループと共有」→ サービスアカウントのメールアドレス（JSONの `client_email` の値）を「**予定の変更**」権限で追加
7. 同じ設定画面の「カレンダーの統合」→「カレンダーID」を控える
8. ターミナルで登録（private_keyはJSONの `private_key` の値を**ダブルクォートで囲んでそのまま**）:
```bash
supabase secrets set GOOGLE_SA_EMAIL=xxxx@xxxx.iam.gserviceaccount.com
supabase secrets set GOOGLE_SA_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----\n"
supabase secrets set GOOGLE_CALENDAR_ID=控えたカレンダーID
```

### 手順16: 関数の再デプロイと動作テスト

```bash
supabase functions deploy create-reservation --no-verify-jwt
supabase functions deploy cancel-reservation --no-verify-jwt
supabase functions deploy admin-notify
```

テスト項目:
1. 2名のテスト予約 → 店長のLINEに【新規予約】が届く＋カレンダーに予定が入る
2. 9名のテスト予約 → LINEに【要電話確認・団体】＋カレンダーに【仮】付き予定
3. 管理画面で仮受付を確定 → カレンダーの【仮】が外れる
4. キャンセルURLからキャンセル → LINEに【キャンセル】＋カレンダーから予定が消える
5. 通知の成否は `notification_log` テーブル（channel = line / gcal）で確認できる

## トラブルのとき

- メールが届かない → Resendダッシュボードの「Logs」を確認。Domainが「Verified」か確認
- 「認証に失敗しました」が出る → Turnstile の Site Key / Secret Key の組み合わせを確認
- 予約が入らない → Supabase の「Edge Functions」→ 対象関数 → Logs を確認
